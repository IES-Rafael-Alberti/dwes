# Usuarios, perfiles y roles con JPA en `bshipAlong`

Este recorrido continúa el trabajo de persistencia, después de las guías 10 y 11.
Construiremos un modelo de identidades **para estudiar relaciones y preparar la
seguridad posterior**. No añadimos login, contraseñas, registro público, endpoints,
permisos efectivos ni jugadores a las partidas: los roles de esta guía son datos,
no autorizaciones. Tampoco se modifica la tarea Book Catalog.

**Punto de partida:** migraciones V1–V4, consultas y pruebas del proyecto de aula.
La preparación docente se verificó sobre una copia con las guías 10 y 11 ya
aplicadas; si el aula queda en otro punto, contrasta las diferencias antes de
seguir. Ejecuta los comandos desde la raíz de `bshipAlong`.

## 1. El problema y el diseño

Una cuenta identifica a una persona en la aplicación. Su perfil contiene datos
visibles, como el nombre que desea mostrar. Un rol describe una categoría de
acceso, como `PLAYER`; en esta guía **todavía no concede permisos**.

- Una cuenta puede existir sin perfil; cada perfil pertenece a **una** cuenta.
  La clave foránea única impide que una cuenta tenga dos perfiles: relación 1:1.
- Una cuenta puede tener varios roles y un rol puede compartirse entre cuentas:
  relación N:M mediante una tabla intermedia. Puede no tener ninguno.
- Un nombre de usuario y un nombre de rol no pueden repetirse exactamente. La
  sensibilidad a mayúsculas y la normalización dependen de la BD y de una futura
  política de aplicación; aquí no prometemos equivalencia entre `Ana` y `ana`.

Esquema: `app_user 1 ← 0..1 user_profile`; `app_user N ↔ M app_role`, a
través de `user_role`. Separamos `AppUser` y `AppRole` de las palabras SQL
`user` y `role`. Los tipos son deliberadamente pequeños: aún no contienen datos
de autenticación ni se devuelven como entidades por HTTP.

**Sobre los tableros:** en el modelo actual una partida tiene un tablero. Esta
lección no asocia cuentas a partidas; antes de implementar multijugador hará
falta diseñar `Board`, migrar barcos/ataques y sus restricciones por tablero.
No tomes esta lección como implementación de dos jugadores.

## 2. Migración Flyway: tablas y restricciones

Si V1–V4 ya existen y no hay otra V5, añade el archivo siguiente. Si ya se ha
usado V5, elige con el profesor el siguiente número libre y ajusta el nombre;
**no edites una migración ya aplicada**. Esta migración reserva V5 para
identidades; la futura migración de tableros deberá usar la siguiente versión
libre. No borres bases ni volúmenes para resolver discrepancias.

**Archivo:** `src/main/resources/db/migration/V5__create_user_profile_role.sql`

```sql
CREATE TABLE app_user (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    username VARCHAR(80) NOT NULL,
    CONSTRAINT uk_app_user_username UNIQUE (username)
);

CREATE TABLE user_profile (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    display_name VARCHAR(100) NOT NULL,
    user_id BIGINT NOT NULL,
    CONSTRAINT uk_profile_user UNIQUE (user_id),
    CONSTRAINT fk_profile_user FOREIGN KEY (user_id) REFERENCES app_user(id)
);

CREATE TABLE app_role (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(40) NOT NULL,
    CONSTRAINT uk_role_name UNIQUE (name)
);

CREATE TABLE user_role (
    user_id BIGINT NOT NULL,
    role_id BIGINT NOT NULL,
    PRIMARY KEY (user_id, role_id),
    CONSTRAINT fk_user_role_user FOREIGN KEY (user_id) REFERENCES app_user(id),
    CONSTRAINT fk_user_role_role FOREIGN KEY (role_id) REFERENCES app_role(id)
);
```

La restricción `uk_profile_user` garantiza como máximo un perfil por cuenta;
`NOT NULL` garantiza que no hay perfil sin cuenta. La clave primaria compuesta
de `user_role` evita repetir la misma asignación. No equivale a un `ON DELETE
CASCADE`: no se ha definido el borrado automático de usuarios o roles.

> La prueba independiente PostgreSQL anterior comprueba exactamente cuatro
> migraciones. **Después de aplicar V5**, si se vuelve a ejecutar contra una BD
> actualizada, su expectativa de `count(*)` debe cambiarse de 4 a 5; de lo
> contrario fallará aunque la migración sea correcta. No cambiarla antes de
> aplicar V5 ni afirmar que PostgreSQL está verificado sin ejecutar la prueba.

## 3. Entidades: cuenta y perfil

Primero prepararemos también el tipo `AppRole` porque la cuenta lo utiliza en
su conjunto de roles. Esto es preparación estructural; la relación N:M y su
comprobación se explican en el apartado 4. No se incorporan reglas de seguridad.

**Archivo:** `src/main/java/es/daw2a/bshipalong/domain/AppRole.java`

```java
package es.daw2a.bshipalong.domain;

import jakarta.persistence.*;

@Entity
@Table(name = "app_role")
public class AppRole {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    @Column(nullable = false, length = 40)
    private String name;

    protected AppRole() {}
    public AppRole(String name) { this.name = name; }
    public Long getId() { return id; }
    public String getName() { return name; }
}
```

**Archivo:** `src/main/java/es/daw2a/bshipalong/domain/AppUser.java`

```java
package es.daw2a.bshipalong.domain;

import jakarta.persistence.*;
import java.util.HashSet;
import java.util.Set;

@Entity
@Table(name = "app_user")
public class AppUser {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    @Column(nullable = false, length = 80)
    private String username;

    @ManyToMany(fetch = FetchType.LAZY)
    @JoinTable(name = "user_role",
            joinColumns = @JoinColumn(name = "user_id"),
            inverseJoinColumns = @JoinColumn(name = "role_id"))
    private Set<AppRole> roles = new HashSet<>();

    protected AppUser() {}
    public AppUser(String username) { this.username = username; }
    public Long getId() { return id; }
    public String getUsername() { return username; }
    public Set<AppRole> getRoles() { return roles; }
    public void addRole(AppRole role) { roles.add(role); }
    public void removeRole(AppRole role) { roles.remove(role); }
}
```

**Archivo:** `src/main/java/es/daw2a/bshipalong/domain/UserProfile.java`

```java
package es.daw2a.bshipalong.domain;

import jakarta.persistence.*;

@Entity
@Table(name = "user_profile")
public class UserProfile {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    @Column(name = "display_name", nullable = false, length = 100)
    private String displayName;
    @OneToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "user_id", nullable = false, unique = true)
    private AppUser user;

    protected UserProfile() {}
    public UserProfile(AppUser user, String displayName) {
        this.user = user;
        this.displayName = displayName;
    }
    public Long getId() { return id; }
    public String getDisplayName() { return displayName; }
    public AppUser getUser() { return user; }
}
```

`UserProfile.user` es el **lado propietario**: su `@JoinColumn` corresponde a
`user_profile.user_id`. No añadimos una referencia inversa en `AppUser` porque
no la necesitamos para este corte; por tanto, no hay aquí una navegación
bidireccional que serializar. `LAZY` expresa una preferencia de carga, no una
promesa universal sobre el SQL que ejecutará el proveedor.

El `Set<AppRole>` vive en la cuenta y `@JoinTable` describe las dos columnas
FK de `user_role`. Se guardan referencias a roles existentes; no se ha activado
`CascadeType.REMOVE`, que podría borrar un rol compartido por otras cuentas.
No usamos Lombok `@Data` ni generamos `equals`/`hashCode` sobre relaciones.
El `Set` evita repetir la misma instancia en memoria; la PK compuesta es la
protección persistente. No se garantiza con ello que dos objetos Java distintos
que representen la misma fila sean iguales en memoria.

## 4. Repositorios

Creamos tres repositorios, sin añadir todavía controladores ni servicios de alta:

**Archivo:** `src/main/java/es/daw2a/bshipalong/repository/AppUserRepository.java`

```java
package es.daw2a.bshipalong.repository;

import es.daw2a.bshipalong.domain.AppUser;
import org.springframework.data.jpa.repository.JpaRepository;
import java.util.Optional;

public interface AppUserRepository extends JpaRepository<AppUser, Long> {
    Optional<AppUser> findByUsername(String username);
}
```

**Archivo:** `src/main/java/es/daw2a/bshipalong/repository/UserProfileRepository.java`

```java
package es.daw2a.bshipalong.repository;

import es.daw2a.bshipalong.domain.UserProfile;
import org.springframework.data.jpa.repository.JpaRepository;
import java.util.Optional;

public interface UserProfileRepository extends JpaRepository<UserProfile, Long> {
    Optional<UserProfile> findByUser_Id(Long userId);

```

**Archivo:** `src/main/java/es/daw2a/bshipalong/repository/AppRoleRepository.java`

```java
package es.daw2a.bshipalong.repository;

import es.daw2a.bshipalong.domain.AppRole;
import org.springframework.data.jpa.repository.JpaRepository;
import java.util.Optional;

public interface AppRoleRepository extends JpaRepository<AppRole, Long> {
    Optional<AppRole> findByName(String name);
}
```

`findByUser_Id` navega por la propiedad Java `user` y su `id`; el guion bajo
separa expresamente las propiedades. Las consultas devuelven `Optional` porque
puede no existir un perfil, una cuenta o un rol con el valor buscado.

## 5. Pruebas de relaciones y restricciones

La clase siguiente usa H2 aislado, `@Transactional` y datos propios. `flush`
fuerza la escritura antes de comprobar restricciones y `clear` evita que una
lectura se resuelva solo con objetos que ya estaban en el contexto de JPA.
Las pruebas que provocan errores de BD son independientes: cada una tiene su
propia transacción y no intenta continuar tras la violación.

**Archivo:** `src/test/java/es/daw2a/bshipalong/repository/IdentityPersistenceTest.java`

```java
package es.daw2a.bshipalong.repository;

import es.daw2a.bshipalong.domain.AppRole;
import es.daw2a.bshipalong.domain.AppUser;
import es.daw2a.bshipalong.domain.UserProfile;
import jakarta.persistence.EntityManager;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.dao.DataIntegrityViolationException;
import org.springframework.transaction.annotation.Transactional;

import static org.assertj.core.api.Assertions.assertThat;
import static org.assertj.core.api.Assertions.assertThatThrownBy;

@SpringBootTest
@Transactional
class IdentityPersistenceTest {
    @Autowired AppUserRepository users;
    @Autowired UserProfileRepository profiles;
    @Autowired AppRoleRepository roles;
    @Autowired EntityManager em;

    @Test
    void userCanExistWithoutProfile() {
        var user = users.saveAndFlush(new AppUser("ana"));
        assertThat(profiles.findByUser_Id(user.getId())).isEmpty();
    }

    @Test
    void profileReferencesOneUser() {
        var user = users.saveAndFlush(new AppUser("bea"));
        profiles.saveAndFlush(new UserProfile(user, "Bea"));
        em.clear();
        var profile = profiles.findByUser_Id(user.getId()).orElseThrow();
        assertThat(profile.getDisplayName()).isEqualTo("Bea");
        assertThat(profile.getUser().getUsername()).isEqualTo("bea");
    }

    @Test
    void databaseRejectsTwoProfilesForTheSameUser() {
        var user = users.saveAndFlush(new AppUser("carla"));
        profiles.saveAndFlush(new UserProfile(user, "Carla"));
        assertThatThrownBy(() -> profiles.saveAndFlush(new UserProfile(user, "Otra")))
                .isInstanceOf(DataIntegrityViolationException.class);
    }

    @Test
    void databaseRejectsDuplicateUsernames() {
        users.saveAndFlush(new AppUser("daniel"));
        assertThatThrownBy(() -> users.saveAndFlush(new AppUser("daniel")))
                .isInstanceOf(DataIntegrityViolationException.class);
    }

    @Test
    void usersShareRoleAndRemovingAssignmentKeepsRole() {
        AppRole player = roles.saveAndFlush(new AppRole("PLAYER"));
        AppUser first = users.saveAndFlush(new AppUser("eva"));
        AppUser second = users.saveAndFlush(new AppUser("fran"));
        first.addRole(player);
        first.addRole(player);
        second.addRole(player);
        users.saveAndFlush(first);
        users.saveAndFlush(second);
        Long firstId = first.getId(), secondId = second.getId(), roleId = player.getId();
        em.clear();

        AppUser loaded = users.findById(firstId).orElseThrow();
        assertThat(loaded.getRoles()).extracting(AppRole::getName).containsExactly("PLAYER");
        loaded.removeRole(loaded.getRoles().iterator().next());
        users.saveAndFlush(loaded);
        em.clear();

        assertThat(users.findById(firstId).orElseThrow().getRoles()).isEmpty();
        assertThat(users.findById(secondId).orElseThrow().getRoles())
                .extracting(AppRole::getName).containsExactly("PLAYER");
        assertThat(roles.findById(roleId)).isPresent();
    }
}
```

Ejecuta desde `bshipAlong`:

```bash
./mvnw -Dtest=IdentityPersistenceTest test
./mvnw test
```

Comprueba que pasan las cinco pruebas nuevas y la suite completa. El resultado
concreto depende de las pruebas que tenga tu proyecto. H2 ayuda a verificar la
lógica, pero no reemplaza una comprobación posterior de la migración en
PostgreSQL. Usa solo una BD de prueba controlada, sin exponer credenciales.

## 6. Qué hemos demostrado y qué no

Hemos comprobado que puede haber una cuenta sin perfil, que un perfil apunta a
una cuenta, que la BD rechaza nombres duplicados y dos perfiles para la misma
cuenta, y que un rol compartido sobrevive al retirar una asignación. No hemos
comprobado todavía alta de usuarios, autenticación, autorización, política de
borrado, normalización de nombres, validación de entrada HTTP ni exposición de
DTO. No debemos dar permisos por aceptar un rol arbitrario de un cliente.

Para repasar:

1. ¿En qué tabla está la FK que representa la relación 1:1? ¿Qué evita `UNIQUE`?
2. ¿Por qué una cuenta puede no tener perfil, pero un perfil no puede carecer de cuenta?
3. ¿Por qué hay una tabla `user_role` y por qué su PK tiene dos columnas?
4. ¿Qué riesgo tendría propagar el borrado de una cuenta a los roles compartidos?
5. ¿Por qué una prueba H2 verde no acredita que se probó PostgreSQL?
