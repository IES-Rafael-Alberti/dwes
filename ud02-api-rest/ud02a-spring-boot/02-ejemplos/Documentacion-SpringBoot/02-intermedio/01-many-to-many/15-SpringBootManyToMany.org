* Many to many relationship in Spring Boot Data REST
Supose we have a mechanic that works in a workshop. A garage may have
several mechanics. A mechanic can repair many cars. A car can be
repaired by several mechanics. We need to model this with Spring Data
REST.

We can use three entity classes: Mechanic, Garage, and Car.  The
Mechanic entity would have a many-to-many relationship with the Car
entity, and the Garage entity would have a one-to-many relationship
with the Mechanic entity.

You can annotate the Mechanic entity with @ManyToMany and use the
@JoinTable annotation to specify the join table that will be used to
link Mechanics and Cars. The Car entity would have a corresponding
@ManyToMany annotation to establish the relationship in the other
direction.

The Garage entity would have a @OneToMany relationship with Mechanic,
and you can use the @JoinColumn annotation to specify the foreign key
that links Mechanic to Garage.

Spring Data REST will then automatically expose REST endpoints for
these entities, allowing you to create, read, update, and delete
records using HTTP requests.

We can specify the join table between Mechanic and Car in Spring Data
REST, and also include an additional attribute, such as the date of
repair, specific to each Mechanic-Car relationship.  To specify the
join table and include an additional attribute, you can create a
separate entity class that represents the join table. This class
should have two @ManyToOne annotations to represent the Mechanic and
Car entities, and an additional attribute for the date of repair.

You can then use Spring Data REST to expose endpoints for
MechanicCarRepair, Mechanic, and Car entities, allowing you to create,
read, update, and delete records using HTTP requests.

annotation specifies the name of the join table and the foreign keys

If you are using a join table to model the many-to-many relationship
between Car and Mechanic, then you only need to specify the join table
in one of the entities. It doesn't matter which one you choose, as
long as you are consistent in your choice across your entire
application.

In the example I provided earlier where we used a join table, we
specified the @JoinTable annotation on the Car entity. This is because
we assumed that the relationship is bidirectional and the owning side
is the Car entity. Therefore, the Mechanic entity only needed to
specify the other side of the relationship using the "mappedBy"
attribute in the @ManyToMany annotation.

In this example, the @JoinTable annotation is only specified on the
Car entity, and the Mechanic entity uses the "mappedBy" attribute to
specify the other side of the relationship.

If you're using a separate join entity, then you don't need to specify
the join table in either the Car or Mechanic entities, because the
relationship is modeled through the join entity instead.


** Without specifying a Jointable and only ManyToOne, OneToMany relationship

It is not necessary to specify the join table in the Mechanic entity
when using a separate join entity like MechanicCarRepair to model the
relationship between Mechanic and Car. In this case, the relationship
between Mechanic and MechanicCarRepair would be a one-to-many
relationship, and the Mechanic entity would have a collection of
MechanicCarRepair instances.

look like in Java using Spring Data JPA annotations, with the
Mechanic-Car relationship modeled using MechanicCarRepair as a
separate join entity:

** ManyToMany vs several OneToMany, ManyToOne relationships
The choice between using a many-to-many relationship with a join table
versus using two one-to-many relationships with a separate join entity
depends on your specific use case and design preferences.

Here are some factors to consider when deciding between the two
options:

Using a many-to-many relationship with a join table:
 - This option is simpler and requires fewer entities to model the
   relationship.
 - However, it may not be as flexible as using a separate join entity,
   as you may need to add additional attributes to the join table in
   the future.

Using two one-to-many relationships with a separate join entity:
 - This option provides more flexibility, as you can add additional
   attributes to the join entity if needed.
 - However, it requires an additional entity to model the
   relationship, which can make the code more complex.

In general, if the relationship between Car and Mechanic is simple and
doesn't require any additional attributes beyond the IDs of the
related entities, using a many-to-many relationship with a join table
is a good option. It is simpler and requires fewer entities to model
the relationship.

If you anticipate that you may need to add additional attributes to
the relationship in the future, or if the relationship is more complex
(e.g., a car can have multiple mechanics, but each mechanic has a
different role in the repair process), then using two one-to-many
relationships with a separate join entity may be a better option.

Ultimately, the best approach depends on the specific requirements and
design of your application.

#+begin_src java
@RestController
@RequestMapping("/mechanic-car-repairs")
public class MechanicCarRepairController {
  private final MechanicCarRepairRepository repository;
  private final CarRepository carRepository;
  private final MechanicRepository mechanicRepository;

  public MechanicCarRepairController(
                  MechanicCarRepairRepository repository,
                  CarRepository carRepository,
                  MechanicRepository mechanicRepository) {
      this.repository = repository;
      this.carRepository = carRepository;
      this.mechanicRepository = mechanicRepository;
  }

  @GetMapping
  public List<MechanicCarRepair> getAll() {
      return repository.findAll();
  }

  @GetMapping("/{id}")
  public MechanicCarRepair getById(@PathVariable Long id) {
    return repository.findById(id)
       .orElseThrow(() ->
       new ResponseStatusException(HttpStatus.NOT_FOUND));
  }

  @PostMapping
  public MechanicCarRepair create(
          @RequestBody MechanicCarRepairRequest request) {
   Car car = carRepository.findById(request.getCarId())
       .orElseThrow(() ->
        new ResponseStatusException(HttpStatus.NOT_FOUND,
                                        "Car not found"));

   Mechanic mechanic = mechanicRepository
     .findById(request.getMechanicId())
     .orElseThrow(() ->
      new ResponseStatusException(HttpStatus.NOT_FOUND,
                                    "Mechanic not found"));
   MechanicCarRepair repair =
       new MechanicCarRepair(request.getDate(), car, mechanic);

   return repository.save(repair);
  }
}

** Temporaly disble Security
While developing, perhaps, we want to disable security checks. There
are two main ways:

1. Create a new configuration that disables security. You can create a
   new configuration class that extends WebSecurityConfigurerAdapter
   and overrides the configure() method to disable security. Here is
   an example:
   #+begin_src java
   @Configuration
   @Order(SecurityProperties.BASIC_AUTH_ORDER)
   public class SecurityConfiguration extends
                      WebSecurityConfigurerAdapter {

       @Override
       protected void configure(HttpSecurity http) throws Exception {
           http.authorizeRequests()
                   .anyRequest().permitAll()
                   .and()
                   .csrf().disable();
       }
   }
   #+end_src

   We need this dependency:
   #+begin_src xml
   <dependency>
   		<groupId>org.springframework.security</groupId>
   		<artifactId>spring-security-config</artifactId>
   	</dependency>
   #+end_src

   This configuration disables security for all endpoints by permitting
   access to all requests. Additionally, it disables Cross-Site Request
   Forgery (CSRF) protection, which is not recommended in production
   environments but may be useful for testing and development.

2. Use Spring Boot's built-in security properties to disable
   security. You can add the following properties to your
   application.properties or application.yml file to disable security:
   #+begin_src
   spring.security.user.password=none
   spring.security.user.name=none
   #+end_src

   This configuration sets the username and password to "none",
   effectively disabling authentication for all requests.

   Note that this method is not recommended for production environments,
   as it leaves your application completely open to attack. However, it
   can be useful for testing and development.

First way is now deprecated, while looking for a new solution both still correct.
