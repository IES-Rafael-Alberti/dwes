## 1. La integridad necesita varias defensas

Una petición puede ser inválida antes de consultar la BD, incumplir una regla de
negocio o chocar con un dato que otra petición acaba de guardar.

| Nivel | Responsabilidad | Ejemplo |
|---|---|---|
| Entrada / Bean Validation | Forma y restricciones locales de los datos recibidos | Nombre no vacío, tamaño permitido |
| Entidad y servicio | Reglas y coordinación del caso de uso | No colocar un barco en una partida ganada |
| Base de datos | Invariantes que deben resistir cualquier escritura válida para el motor | FK, no nulo, nombre único dentro de una partida |
| Capa HTTP | Traducir el resultado al contrato público | 400, 404 o conflicto según la causa |

No conviene preguntar «¿valido en Java o en SQL?» como si hubiera que escoger
uno solo. Son garantías complementarias. Un mensaje temprano ayuda al usuario;
una restricción protege el dato incluso cuando dos peticiones compiten o cuando
la escritura no viene del mismo controlador.

Tampoco toda regla se expresa fácilmente con un `CHECK`. El solapamiento de
barcos, por ejemplo, requiere examinar posiciones y reglas que no se resuelven
añadiendo un `UNIQUE` al nombre.

## 2. PK, FK y claves candidatas

### 2.1. Clave primaria técnica

`ship.id` identifica la fila de un barco. Que cada fila tenga un id diferente no
impide que dos filas representen el mismo barco lógico según nuestras reglas.

```text
id    game_id    ship_name
12       7          A
13       7          A
```

Los ids son distintos, pero la pareja `(game_id, ship_name)` se repite. Si el
negocio prohíbe repetir nombre dentro de una partida, la PK no basta.

### 2.2. Clave foránea

La FK asegura que una referencia no apunte a una fila inexistente, dentro de
las condiciones de nulabilidad y acciones de borrado que hayamos definido.

```sql
game_id BIGINT NOT NULL REFERENCES game(id)
```

No garantiza que la partida esté activa, en curso o autorizada para ese usuario.
Una partida cancelada sigue existiendo y puede seguir siendo un destino válido
para la FK, aunque el servicio prohíba nuevas jugadas sobre ella.

### 2.3. Clave candidata o restricción alternativa

Un conjunto mínimo de atributos que identifica una fila puede ser una clave
candidata. Elegir un id generado como PK no elimina la necesidad de proteger
otras identificaciones que el negocio considere únicas.

En diseño relacional, una clave candidata no admite nulos. Un `UNIQUE` SQL puede
tener un comportamiento distinto con nulos según el motor. Por eso, si los
atributos forman una identificación obligatoria, combinamos unicidad con `NOT NULL`.

## 3. Unicidad simple y unicidad compuesta

### 3.1. Un solo campo

Un nombre de usuario puede ser único sin ser la PK de la tabla:

```sql
CREATE TABLE account_example (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    username VARCHAR(50) NOT NULL,
    CONSTRAINT uk_account_example_username UNIQUE (username)
);
```

Es un ejemplo independiente para explicar el concepto. La incorporación de
usuarios reales se hará en el bloque C; no se crea esta tabla de demostración
dentro del juego únicamente para poder mostrar una restricción simple.

En el mapeo JPA de una entidad correspondiente podríamos expresar:

```java
@Column(nullable = false, unique = true, length = 50)
private String username;
```

La anotación describe el mapeo y puede participar en la generación del esquema
cuando se utiliza ese mecanismo. **Con Flyway y validación de esquema, no crea
por sí sola la restricción que falte en una BD ya existente.**

### 3.2. Una combinación de campos

En el juego hay dos restricciones naturales:

```sql
UNIQUE (game_id, ship_name)
UNIQUE (game_id, x, y)
```

La primera no significa que `game_id` sea único ni que `ship_name` sea único
globalmente. La segunda admite el mismo punto en otra partida.

| Datos existentes | Nueva escritura | Resultado |
|---|---|---|
| Partida 7, barco A | Partida 7, barco A | Rechazo |
| Partida 7, barco A | Partida 8, barco A | Permitido por esa restricción |
| Partida 7, ataque (2,3) | Partida 7, ataque (2,3) | Rechazo |
| Partida 7, ataque (2,3) | Partida 8, ataque (2,3) | Permitido por esa restricción |
| Partida 7, ataque (2,3) | Partida 7, ataque (3,2) | Permitido por esa restricción |

«Permitido por esa restricción» no implica que la operación cumpla todas las
reglas del servicio. Por ejemplo, atacar una partida pendiente puede seguir
estando prohibido.

### 3.3. Expresarlo en JPA

En la clase `Ship`, la anotación de tabla puede quedar así:

```java
@Table(name = "ship", uniqueConstraints = {
    @UniqueConstraint(name = "uk_ship_game_name",
                      columnNames = {"game_id", "ship_name"})
})
```

Y en `Attack`:

```java
@Table(name = "attack", uniqueConstraints = {
    @UniqueConstraint(name = "uk_attack_game_point",
                      columnNames = {"game_id", "x", "y"})
})
```

`columnNames` contiene **nombres de columnas**, no atributos Java. Por eso usamos
`game_id`, aunque la asociación se llame `game`, y `ship_name`, aunque el atributo
sea `shipName`. Es justo lo contrario de `mappedBy`, que nombra un atributo Java.

No hace falta duplicar una restricción simple equivalente en `@Column` y
`@Table`. Lo importante es que modelo, migración y pruebas expresen la misma regla.

## 4. Qué significa realmente «igual»

Antes de imponer unicidad hay que decidir qué datos considera iguales el dominio.

- ¿`Ana` y `ana` representan el mismo nombre de usuario?
- ¿Se recortan espacios iniciales y finales?
- ¿Un nombre de barco puede cambiarse? ¿Con qué reglas?
- ¿La unicidad se mantiene después de una baja lógica?

No se resuelve todo con una llamada a `toLowerCase`. La normalización, colación
y tipo de restricción deben ser coherentes. Una política aplicada solo en un
controlador puede saltarse desde otra ruta de escritura.

En Battleship, el nombre se protege dentro de la partida. Como cancelar conserva
el histórico, no se libera automáticamente esa combinación. Si otro dominio
permite reutilizar identificaciones tras una baja, necesitará un diseño distinto,
posiblemente específico del motor; no se presupone con un `UNIQUE` ordinario.

### 4.1. Nulos en restricciones compuestas

No debemos depender de que una pareja como `(game_id, NULL)` se comporte como
un nombre válido único. `ship_name` es obligatorio y su columna no admite nulos.

Bean Validation puede rechazar un nombre en blanco, pero `NOT NULL` no rechaza
por sí solo una cadena de espacios. Las condiciones deben repartirse con intención.

## 5. Por qué una preconsulta no garantiza unicidad

Esta comprobación puede dar un mensaje útil:

```java
if (shipRepository.existsByGame_IdAndShipName(gameId, name)) {
    throw new IllegalArgumentException("Ship name already used");
}
```

El método supuesto corresponde al modelo con `Ship.game`; su implementación
derivada se estudiará en el bloque B. No debe confundirse con el método basado
en el antiguo campo numérico `gameId`.

El problema aparece con dos peticiones concurrentes:

```text
Petición A: consulta «¿existe A en partida 7?» → no
Petición B: consulta «¿existe A en partida 7?» → no
Petición A: inserta
Petición B: intenta insertar
```

Sin restricción de BD, ambas podrían guardar el duplicado. Con la restricción,
una escritura se rechaza. La preconsulta sigue siendo útil, pero no es la última
defensa. Una transacción ordinaria no convierte automáticamente ese patrón en
una exclusión mutua.

### 5.1. Comprobar unicidad al actualizar

Al editar un nombre de usuario no se debe rechazar la propia fila por conservar
su nombre. La consulta de aplicación puede excluir el id actual. La restricción
de BD, en cambio, ya evalúa el estado que resulta de la escritura: no necesita
un validador distinto por cada formulario.

En entidades nuevas todavía no existe id generado; el código que decide si es
alta o edición debe tratarlo explícitamente.

## 6. Evolucionar el esquema con Flyway

El proyecto de aula ya tiene V1, V2 y V3. Una modificación nueva debe utilizar
una versión libre posterior. **No se cambia V3 después de haberla aplicado**
para hacer que parezca que la restricción existió siempre.

Si V4 sigue libre, una migración podría llamarse
`V4__add_game_integrity_constraints.sql` y contener:

<!-- ejemplo-sql: V4__add_game_integrity_constraints.sql -->
```sql
ALTER TABLE ship
    ADD CONSTRAINT uk_ship_game_name UNIQUE (game_id, ship_name);

ALTER TABLE attack
    ADD CONSTRAINT uk_attack_game_point UNIQUE (game_id, x, y);
```

El nombre concreto se decide al preparar el checkpoint. Si otra migración ya usa
esa versión, se elige la siguiente: no se fuerza el número por copiar el ejemplo.

### 6.1. Mirar los datos existentes antes de añadir la restricción

```sql
SELECT game_id, ship_name, COUNT(*) AS repetitions
FROM ship
GROUP BY game_id, ship_name
HAVING COUNT(*) > 1;

SELECT game_id, x, y, COUNT(*) AS repetitions
FROM attack
GROUP BY game_id, x, y
HAVING COUNT(*) > 1;
```

Si existen duplicados, la migración puede fallar. Hace falta una decisión sobre
esos datos: corregirlos, fusionarlos o rechazarlos según el caso. Borrarlos
automáticamente para que la migración «pase» puede destruir información válida.

Para el entorno de estudio podemos preparar datos consistentes y probar también
el rechazo de una base con duplicados. No se exige al alumnado una herramienta
de limpieza universal.

### 6.2. La FK puede seguir siendo la misma al cambiar Java

Pasar de `Long gameId` a `Game game` no obliga a renombrar `game_id` ni a copiar
las filas a otra tabla. Puede cambiar el mapeo Java manteniendo el mismo esquema
físico, si ambas representaciones usan esa columna de forma compatible.

Es otra razón para distinguir **refactorización del modelo**, **cambio de esquema**
y **cambio del contrato HTTP**. No tienen por qué hacerse a la vez.

### 6.3. Un solo responsable del esquema

```yaml
spring:
  jpa:
    hibernate:
      ddl-auto: validate
    open-in-view: false
```

En esta configuración, Flyway aplica las migraciones y Hibernate comprueba la
compatibilidad básica del mapeo al arrancar. `validate` no debe considerarse una
auditoría exhaustiva de todas las restricciones únicas y reglas del esquema.

No activar `ddl-auto=update` para que Hibernate «arregle» lo que olvidó la migración.
Tampoco mezclar otro `schema.sql` que cree las mismas tablas. Eso escondería el
problema de reproducibilidad en vez de resolverlo.

## 7. Transacción: una unidad de trabajo coherente

Una transacción agrupa cambios que deben confirmarse o deshacerse juntos. El
servicio es el lugar habitual para delimitar un caso de uso que utiliza varios
repositorios y modifica varias entidades.

```java
@Transactional
public void cancelGame(Long id) {
    Game game = findActiveGame(id);
    game.cancel();
    // La entidad gestionada cambia dentro de la unidad de trabajo.
}
```

El ejemplo supone que la partida se recupera en esa misma unidad de trabajo.
No significa que cualquier objeto modificado en cualquier lugar vaya a guardarse.

### 7.1. Cuándo aparece una violación de integridad

Según la estrategia de generación de ids, el proveedor y el motor, un error puede
aparecer durante `persist`, durante `save`, en un flush posterior o al confirmar.
Con `IDENTITY`, algunos INSERT se necesitan pronto para obtener el id.

Por eso, esta secuencia no es una garantía general:

```java
try {
    repository.save(entity);
} catch (DataIntegrityViolationException ex) {
    // No necesariamente se detectará aquí una escritura diferida.
}
```

`saveAndFlush` fuerza la sincronización pendiente, pero no confirma la transacción.
Puede adelantar la detección de un error; no es una solución universal que haya
que colocar en todos los guardados.

### 7.2. Después de un error, no continuar como si nada

Una transacción o un contexto que ha sufrido un fallo de persistencia no debe
reutilizarse para «probar otra cosa» y luego confirmar. El flujo debe finalizar
con rollback y el tratamiento público correspondiente.

Capturar la excepción dentro del servicio y continuar puede acabar en otro error
al commit, por ejemplo porque la transacción quedó marcada para rollback. El
traductor HTTP debe actuar en el límite adecuado, no convertir una operación
fallida en un falso éxito.

## 8. Traducir el fallo sin perder su significado

Con repositorios Spring, muchas excepciones de persistencia se traducen a la
jerarquía de acceso a datos de Spring. `DataIntegrityViolationException` es amplia:
puede representar una FK, un no nulo o una unicidad incumplida, entre otras causas.

No debemos asumir que siempre significa «el nombre está repetido». Tampoco se
devuelve el mensaje SQL interno, el nombre de la tabla o la traza al cliente.

Una política de aplicación puede distinguir una excepción de negocio conocida
del fallo de integridad inesperado. Si se decide reconocer una restricción por
su nombre o metadatos del proveedor, ese reconocimiento debe estar acotado y
probado; no se analiza una cadena de error arbitraria como única API estable.

### 8.1. ¿400 o 409?

Un dato mal formado puede ser 400; una colisión con el estado o recursos existentes
puede modelarse como 409. Lo importante es acordar el contrato y mantenerlo.

En el checkpoint previo de Battleship, varias reglas de argumentos se traducen
a 400. **Esta lectura no cambia retroactivamente ese contrato a 409.** Si la
evolución decide distinguir duplicados con una excepción propia, se cambian
deliberadamente test, advice y documentación en el mismo tramo.

La restricción SQL no impone por sí sola un código HTTP: también puede usarse
desde un proceso que ni siquiera recibe peticiones web.

## 9. Qué prueba demuestra cada garantía

| Prueba | Qué puede demostrar | Qué no demuestra |
|---|---|---|
| Unitaria de entidad | Transición y mantenimiento de referencias en memoria | Que la FK o el `UNIQUE` existen |
| Servicio con repositorio mock | Decisiones y llamadas al colaborador simulado | Que la BD rechaza un duplicado |
| Persistencia con BD y esquema migrado | Mapeo, escritura, consulta y restricciones ejecutadas | Todo el contrato HTTP |
| MVC con servicio mock | Traducción HTTP, JSON y delegación | Integridad real ni persistencia |
| Flujo con componentes reales | Conexión entre capas en escenarios escogidos | Todos los casos posibles ni condiciones reales de concurrencia |

No se necesitan cinco pruebas idénticas por operación. Se elige el nivel que
puede detectar el defecto. Para demostrar una restricción SQL, debe ejecutarse
la escritura contra una BD que tenga la migración correspondiente.

### 9.1. `@DataJpaTest` o contexto completo

Un slice JPA permite concentrarse en entidades y repositorios. Su configuración
y módulos de test deben corresponder a Spring Boot 4. No se presupone que ignore
Flyway ni que reconstruya siempre el esquema con Hibernate: comprobar la
configuración efectiva y los logs de arranque.

El ejemplo siguiente usa `@SpringBootTest`, que ya forma parte del recorrido de
aula, y `@Transactional` para aislar las pruebas. Es más amplio que un slice,
pero evita que una configuración de prueba diferente oculte la migración que se
quiere comprobar. No abre un puerto HTTP por utilizar esa anotación.

## 10. Ejemplo de pruebas que sí llegan a la BD

Este ejemplo supone:

- Las entidades `Game`, `Ship` y `Attack` del bloque A, con `setGame` en los hijos
  y colección `getShips` en la partida.
- Los demás atributos obligatorios del juego y sus callbacks de fecha conservados.
- Esquema creado con las migraciones, incluidas las dos restricciones nuevas.
- Configuración de pruebas con aislamiento entre métodos.

**No se copia al checkpoint previo para exigirle un modelo que aún no tiene.**
Se utiliza al aplicar la evolución, conservando sus demás pruebas.

<!-- ejemplo-java: GameIntegrityPersistenceTest.java -->
```java
package es.daw2a.bshipalong.domain;

import jakarta.persistence.EntityManager;
import jakarta.persistence.PersistenceException;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.transaction.annotation.Transactional;

import static org.assertj.core.api.Assertions.assertThat;
import static org.assertj.core.api.Assertions.assertThatThrownBy;

@SpringBootTest
@Transactional
class GameIntegrityPersistenceTest {
    @Autowired EntityManager em;

    private Game game() {
        Game game = new Game(8);
        em.persist(game);
        return game;
    }

    private Ship ship(Game game, String name) {
        Ship ship = new Ship();
        ship.setShipName(name);
        ship.setLength(1);
        ship.setStartX(0);
        ship.setStartY(0);
        ship.setHorizontal(true);
        ship.setSunk(false);
        game.addShip(ship);
        return ship;
    }

    private Attack attack(Game game, int x, int y) {
        Attack attack = new Attack();
        attack.setGame(game);
        attack.setX(x);
        attack.setY(y);
        attack.setHit(false);
        return attack;
    }

    @Test void relationSurvivesFlushAndClear() {
        Game game = game();
        Ship ship = ship(game, "A");
        em.persist(ship);
        em.flush();
        Long gameId = game.getId();
        Long shipId = ship.getId();
        em.clear();

        Ship loaded = em.find(Ship.class, shipId);
        assertThat(loaded.getGame().getId()).isEqualTo(gameId);
        assertThat(em.find(Game.class, gameId).getShips())
                .extracting(Ship::getShipName).containsExactly("A");
    }

    @Test void repeatedNameInSameGameIsRejected() {
        Game game = game();
        em.persist(ship(game, "A"));
        em.flush();

        assertThatThrownBy(() -> {
            em.persist(ship(game, "A"));
            em.flush();
        }).isInstanceOf(PersistenceException.class);
        // Terminar: no hacer más consultas en esta transacción fallida.
    }

    @Test void sameNameInDifferentGamesIsAllowed() {
        em.persist(ship(game(), "A"));
        em.persist(ship(game(), "A"));
        em.flush();
        em.clear();

        Long count = em.createQuery(
                "select count(s) from Ship s where s.shipName = :name", Long.class)
                .setParameter("name", "A").getSingleResult();
        assertThat(count).isEqualTo(2L);
    }

    @Test void repeatedPointInSameGameIsRejected() {
        Game game = game();
        em.persist(attack(game, 2, 3));
        em.flush();

        assertThatThrownBy(() -> {
            em.persist(attack(game, 2, 3));
            em.flush();
        }).isInstanceOf(PersistenceException.class);
    }

    @Test void samePointInDifferentGamesIsAllowed() {
        em.persist(attack(game(), 2, 3));
        em.persist(attack(game(), 2, 3));
        em.flush();
        em.clear();

        Long count = em.createQuery(
                "select count(a) from Attack a where a.x = :x and a.y = :y", Long.class)
                .setParameter("x", 2).setParameter("y", 3).getSingleResult();
        assertThat(count).isEqualTo(2L);
    }

    @Test void cancellingKeepsRelatedRows() {
        Game game = game();
        Ship ship = ship(game, "A");
        em.persist(ship);
        Attack attack = attack(game, 0, 0);
        em.persist(attack);
        em.flush();
        Long gameId = game.getId();
        Long shipId = ship.getId();
        Long attackId = attack.getId();

        game.cancel();
        em.flush();
        em.clear();

        assertThat(em.find(Game.class, gameId).isActive()).isFalse();
        assertThat(em.find(Ship.class, shipId)).isNotNull();
        assertThat(em.find(Attack.class, attackId)).isNotNull();
    }
}
```

Los dos escenarios de duplicado colocan tanto `persist` como `flush` dentro de
la aserción porque el INSERT puede adelantarse. Al usar `EntityManager`
directamente se comprueba una excepción de persistencia; no se exige que Spring
la traduzca como si la llamada hubiera atravesado un repositorio.

Los datos se montan directamente para aislar mapeo e integridad. No se está
afirmando que esos ataques se hayan autorizado mediante el servicio. Las reglas
del juego necesitan sus pruebas de dominio/servicio, que ya existen.

### 10.1. Por qué `flush` y `clear`

Sin `clear`, encontrar una entidad puede devolver la misma instancia ya gestionada.
Eso no demuestra por sí solo que la relación se haya almacenado y reconstruido
desde la BD. El patrón de prueba es:

```text
Preparar → persistir → flush → guardar ids → clear → consultar → comprobar
```

`clear` separa las entidades; no borra filas. Hacerlo antes de sincronizar podría
descartar cambios pendientes. Tampoco debe confundirse con limpiar una tabla.

### 10.2. Lo que aún hay que comprobar aparte

- Arranque desde una BD vacía y migración desde una versión con datos anteriores.
- Que un dato válido previo se conserva tras la nueva migración.
- Que la FK rechaza una escritura con padre inexistente.
- Que la política HTTP de errores coincide con el contrato.
- Que un test transaccional no está ocultando una carga diferida que fallaría
  cuando el controlador trabaja fuera de esa transacción.
- Las diferencias relevantes entre H2 y el motor de destino. H2 real no es
  un mock, pero tampoco prueba automáticamente todos los detalles de PostgreSQL.

No hace falta construir ahora una batería universal. Se selecciona la evidencia
necesaria para cada riesgo concreto y se amplía cuando el caso lo exige.

## 11. Migración reproducible frente a una suite verde engañosa

Una prueba podría pasar porque Hibernate creó un `UNIQUE` a partir de las
anotaciones, aunque la migración esté incompleta. Si producción utiliza solo
Flyway, ese resultado no demuestra la misma garantía allí.

Comprobar al menos:

1. Qué configuración usa realmente el test.
2. Qué motor está activo.
3. Qué migraciones se han aplicado.
4. Que no hay un mecanismo alternativo reparando el esquema por detrás.
5. Que el duplicado se intenta escribir y el caso permitido también se guarda.

Una anotación presente, una llamada a `save` y un test verde con mocks no suman
por sí solos una prueba de integridad de datos.

## 12. Tabla rápida de errores de diseño

| Decisión problemática | Por qué falla | Mejor criterio |
|---|---|---|
| «Ya tiene un id, no necesita más unicidad» | Dos filas con ids distintos pueden violar la misma regla | Identificar también las restricciones del dominio |
| `unique=true` en `ship_name` | Prohíbe ese nombre en todas las partidas | `UNIQUE(game_id, ship_name)` |
| Un `Set` como garantía | Solo controla una colección Java con una igualdad concreta | Restricción de BD más modelo coherente |
| Solo `exists…` antes de guardar | Dos peticiones pueden observar ausencia a la vez | Preconsulta y restricción, con traducción de errores |
| Cambiar V3 ya aplicada | Rompe el historial de evolución | Nueva migración |
| Confiar en `ddl-auto=validate` para todo | No es una auditoría completa de integridad | Migración y prueba de escritura |
| Capturar el error y seguir usando la transacción | Puede estar marcada para rollback o tener el contexto inconsistente | Finalizar la operación y tratar el fallo en el límite |
| Probar duplicados con un mock | El mock devuelve lo programado; no ejecuta SQL | Prueba de persistencia |
| Borrar hijos al cancelar | Destruye el histórico | Baja lógica con filas conservadas |

## 13. Resumen y preguntas de repaso

La cadena de razonamiento que debe poder explicarse es:

```text
Requisito → modelo → restricción/migración → escritura real → evidencia → respuesta pública
```

Preguntas para estudio, no una práctica adicional:
